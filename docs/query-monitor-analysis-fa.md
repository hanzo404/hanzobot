## ۰) خلاصه‌ی مدیریتی (اگر فقط ۶۰ ثانیه وقت دارید)

| # | یافته در لاگ | چه معنایی دارد | اثر تقریبی |
|---|---|---|---|
| ۱ | `wp_head` = **۱.۴۸ ثانیه** | رندر هدر صفحه + نوشتن کش المنتور در دیتابیس | بزرگ‌ترین تک‌مصرف |
| ۲ | `init` = **۰.۸۰ ثانیه** | اجرای افزونه‌ها/قالب و صدها کوئری ریز تکراری | دومین مصرف |
| ۳ | `UPDATE wp_options ... rewrite_rules` با `a:504:{...}` | قواعد ری‌رایت در **هر بازدید** از نو ساخته و (بی‌اثر) ذخیره می‌شود | هر بازدید، هدر رفته |
| ۴ | ~۳۰ کوئری `SELECT option_value ... LIMIT 1` فقط از `hamyar-tools` + ده‌ها کوئری `woodmart_*_show_on_product` | آپشن‌هایی که **وجود ندارند** و هر بار جداگانه پرسیده می‌شوند | صدها کوئری در هر صفحه |
| ۵ | نوشتن `_elementor_element_cache` / `_elementor_css` / `_elementor_page_assets` در `wp_head` | کش المنتور در هر بازدید دوباره در `wp_postmeta` نوشته می‌شود | کوئری‌های نوشتنی سنگین + جدول متا متورم |
| ۶ | `duplicator`, `siteskill-*`, `RTL-CareUnit`, `classic-editor`, `code-snippets` در فرانت‌اند | افزونه‌های مدیریتی در هر بازدید کاربر هم اجرا می‌شوند | کوئری + فایل + زمان اضافه |
| ۷ | هشدار `woodmart` textdomain | قالب، ترجمه را خیلی زود بارگذاری می‌کند (هشدار وردپرس ۶.۷+) | جزئی، ولی نشانه‌ی کد قدیمی |
| ۸ | «آبجکت‌کش پایدار» نامعلوم / احتمالاً ندارد | با نبود Redis، همه‌ی این کوئری‌های تکراری هر بار از MySQL خوانده می‌شوند | ضریب‌دهنده‌ی همه‌ی موارد بالا |

**سه کار با بیشترین بازده، به‌ترتیب:**
۱) نصب آبجکت‌کش پایدار (Redis) ۲) حذف طوفان کوئری‌های آپشن (همین حالا با افزونه‌ی همراه) ۳) تعمیر و قفل‌کردن `rewrite_rules` + مهار نوشتن کش المنتور.

## ۱) تفسیر اعداد: زمان کجا می‌رود؟

| بخش | زمان | چه چیزی آن‌جا اجرا می‌شود |
|---|---|---|
| `plugins_loaded` | ۰.۱۲۱s | بارگذاری ۲۰+ افزونه |
| `after_setup_theme` | ۰.۰۶۵s | قالب Woodmart، ثبت ویژگی‌ها |
| `init` | **۰.۸۰۱s** | ثبت پست‌تایپ/تاکسونومی/رست‌اپی، اجرای کد اسنیپت‌ها، کوئری‌های آپشن |
| `wp` | ۰.۰۸۳s | تشخیص کوئری اصلی، ریدایرکت‌ها |
| `template_redirect` | ۰.۰۳۰s | منطق ووکامرس/سبد خرید |
| `wp_head` | **۱.۴۸۳s** | خروجی `<head>`، CSS/JS، **و نوشتن کش المنتور** |
| `wp_body_open` + `wp_footer` | ۰.۱۲s | ویجت‌ها، اسکریپت‌های قالب |
| `shutdown` | ۰.۰۳۰s | نوشتن‌های پایانی، کرون |

نکته‌ی مهم: این اعداد «زمان هوک‌ها» است، نه زمان کل پاسخ. ولی نسبت‌ها معنادار است:
`wp_head` + `init` ≈ ۷۵٪ زمان اندازه‌گیری‌شده. هر دو هم عمدتاً «کوئری + نوشتن» هستند، نه CPU خالص.

جمع تقریبی زمان همه‌ی کوئری‌های فهرست‌شده‌ی شما (میانگین ~۰.۰۱۲s × صدها کوئری) هم به همین نتیجه می‌رسد:
**گلوگاه اصلی، تعداد و تکرار کوئری‌ها است، نه سنگینی یک کوئری خاص.**

## ۲) یافته‌ها + راه‌حل دقیق

### یافته ۱ — طوفان کوئری‌های «تک‌آپشنی» (Biggest quick win)

**در لاگ چه دیدیم:**
```
SELECT option_value FROM wp_options WHERE option_name='hmyt_enabled' LIMIT 1
SELECT option_value FROM wp_options WHERE option_name='hmyt_contact_widget_settings' LIMIT 1
SELECT option_value FROM wp_options WHERE option_name='wc_gemini_*' LIMIT 1
SELECT option_value FROM wp_options WHERE option_name='xsmscore/config_versions' LIMIT 1
...
SELECT option_value FROM wp_options WHERE option_name='woodmart_گنجایش_show_on_product' LIMIT 1
SELECT option_value FROM wp_options WHERE option_name='woodmart_مناسب مایکروویو_show_on_product' LIMIT 1
```

**علت فنی (از سورس خود وردپرس):** تابع `get_option()` به‌ترتیب کش `alloptions` → لیست `notoptions` → کش `options` → **یک کوئری جدا** را طی می‌کند:
```sql
SELECT option_value FROM wp_options WHERE option_name = '...' LIMIT 1
```
اگر یک افزونه/قالب در حلقه‌ای روی آپشن‌هایی بچرخد که **در دیتابیس وجود ندارند** (یا کش را دور بزند)، برای هر آپشن یک رفت‌وبرگشت به MySQL داریم. الگوی `hmyt_*` و `woodmart_*_show_on_product` دقیقاً همین است.

**راه‌حل ۱ (فوری — همان افزونه‌ی همراه):**
افزونه‌ی «دکتر سرعت هَنزبات» نام این آپشن‌های پرتکرار را «یاد می‌گیرد» و در درخواست بعدی همه را با **یک کوئری `IN (...)`** پر می‌کند و ناموجودها را در `notoptions` علامت می‌زند — همان کاری که هسته در `wp_prime_option_caches()` انجام می‌دهد. یعنی از ~۳۰+ کوئری `hmyt_*` و ده‌ها کوئری `woodmart_*` به **۱ کوئری** می‌رسیم. مقادیر موجود همیشه از دیتابیس خوانده می‌شوند، پس ریسک «مقدار اشتباه» صفر است.

**راه‌حل ۲ (ریشه‌ای):**
- `hamyar-tools`: این افزونه به‌جای استفاده از تنظیمات تجمیعی، هر ماژول را جدا می‌پرسد. اگر توسعه‌دهنده‌اش در دسترس است، یک خط برای او بنویسید: *«از `get_options()` (وردپرس ۶.۴+) یا یک آرایه‌ی واحد تنظیمات با `autoload=true` استفاده کنید.»* تا وقتی اصلاح نشده، راه‌حل ۱ مشکل را کامل پوشش می‌دهد.
- `woodmart_<نام ویژگی>_show_on_product`: این‌ها را در **تنظیمات ویژگی‌های ووکامرس → نمایش ویژگی‌ها در محصول** یک‌جا ذخیره کنید (Woodmart معمولاً گزینه‌ی «نمایش همه‌ی ویژگی‌ها» دارد). اگر تعداد ویژگی‌های محصولات زیاد است و لازمشان ندارید، ویژگی‌های بی‌استفاده را از محصولات حذف یا از نمایش در صفحه‌ی محصول خارج کنید — چون قالب همان‌قدر که ویژگی دارید کوئری می‌زند.

**راه‌حل ۳ (تأثیر چند برابر روی همه‌ی موارد ۱):**
نصب **آبجکت‌کش پایدار** (Redis یا Memcached). با آن، حتی وقتی `get_option()` کش می‌خورد، دیگر هیچ کوئری‌ای به MySQL زده نمی‌شود. در Hostinger/Cpanel معمولاً Redis فعال است؛ افزونه‌ی «Redis Object Cache» را نصب و از `wp-config.php` با `WP_REDIS_HOST` وصل کنید. **اگر قرار باشد فقط یک کار کنید، این است.**

### یافته ۲ — بازنویسی `rewrite_rules` در هر بازدید (`a:504:{...}`)

**در لاگ چه دیدیم:**
```
UPDATE wp_options SET option_value = 'a:504:{...}' WHERE option_name = 'rewrite_rules'
```
این کوئری **نباید** در یک بازدید عادی کاربر اجرا شود. فقط موقع فعال‌سازی افزونه، تغییر ساختار پیوندها یا تغییر قالب اجرا می‌شود.

**علت فنی:** در هسته، `wp_rewrite_rules()` این است:
```php
get_option( 'rewrite_rules' )  // اگر خالی باشد:
// → بازسازی کامل قواعد + update_option('rewrite_rules', $rules)
```
پس دو حالت داریم:
1. **ردیف `rewrite_rules` در جدول نباشد یا خالی باشد**: آن‌وقت **هر درخواست** ۵۰۴ قاعده را می‌سازد. بدتر: `update_option()` روی ردیف ناموجود فقط `UPDATE ... WHERE option_name='rewrite_rules'` می‌زند، ولی ردیف **وجود ندارد** پس صفر ردیف تغییر می‌کند و آپشن هیچ‌وقت ذخیره نمی‌شود → چرخه‌ی بی‌پایان در هر بازدید.
2. **افزونه/کد اسنیپتی** با `delete_option('rewrite_rules')` یا `flush_rewrite_rules()` در جای اشتباه (مثلاً داخل `init`) آن را پاک می‌کند و هر بازدید دوباره می‌سازد.

**راه‌حل:**
- دکمه‌ی **«تعمیر فوری rewrite_rules»** در افزونه‌ی همراه: ردیف را با `INSERT ... ON DUPLICATE KEY UPDATE` می‌سازد و **`autoload = off`** می‌گذارد (چون این آپشن ۴۰+ کیلوبایتی است و نباید هر بازدید در `alloptions` خوانده شود).
- **نگهبان rewrite_rules** (پیش‌فرض فعال): نوشتن‌های تکراری/بی‌اثر را حذف می‌کند و **مقصر را لاگ می‌کند** (بخش «رویدادها» در صفحه‌ی افزونه). اگر مقصر «code-snippets» یا یک افزونه‌ی امنیتی/ری‌دایرکت بود، همان را اصلاح یا غیرفعال کنید.
- در سرچ: «Code Snippets» را باز کنید و بگردید دنبال `flush_rewrite_rules` یا `delete_option('rewrite_rules')`. همچنین در افزونه‌های ریدایرکت/امنیتی/Schema دنبال همین کلمه بگردید. هرجا داخل `init` صدا زده شده، انتقالش دهید به هوک `admin_init` با شرط «فقط وقتی تنظیمات ذخیره شد».
- حدس اول از روی فهرست افزونه‌های شما: **Code Snippets** (کدهای `SELECT id, code, scope, active, priority FROM wp_snippets` در هر درخواست یعنی یک کد اسنیپت هم روی `init` اجرا می‌شود) یا **RTL-CareUnit / siteskill-*** که بررسی مجوز و به‌روزرسانی دارند.

**قبل/بعد را بسنجید:** در Query Monitor تعداد کل کوئری‌ها و بخش `wp_options` را یادداشت کنید؛ با رفع این مورد باید ۱ کوئری نوشتنی سنگین + هزینه‌ی بازسازی ۵۰۴ قاعده در هر بازدید حذف شود.

### یافته ۳ — `wp_head` = ۱.۴۸s: کش المنتور دارد در دیتابیس می‌نویسد

**در لاگ چه دیدیم:**
- `INSERT/UPDATE wp_postmeta ... '_elementor_element_cache'` با مقدار سریالایز بزرگ، در چند نقطه از `wp_head`
- `INSERT ... '_elementor_css'` و `_elementor_page_assets`
- `UPDATE wp_options ... elementor_atomic_cache_validity__popup-trigger-styles-related-posts` در تقریباً هر بازدید، با نقشه‌ی `children` که هر بار بزرگ‌تر می‌شود (شناسه‌های ۱۶۷۰، ۸۳۶۴، ۱۷۰۱، ۱۷۱۵، ۱۲۸۴۰، ۱۳۴۹۲، ۱۲۸۳۹ …)
- کوئری‌های `SELECT * FROM wp_posts WHERE post_parent = N AND post_name LIKE 'N-autosave%'` برای ده‌ها نوشته

**علت:** المنتور (نسخه‌های ۳.۲۲+ با «Element Cache / Atomic Widgets») خروجی هر ویجت/پاپ‌آپ را کش می‌کند. اگر محتوای صفحه چیزی باشد که در هر درخواست «تغییر» تلقی شود (تاریخ، قیمت متغیر، نام کاربر، شمارنده، شورت‌کد داینامیک، یا **آخرین نوشته/محصولات مرتبط**)، آن کش در هر بازدید invalidate و **دوباره نوشته** می‌شود. حجم هر ردیف `_elementor_element_cache` می‌تواند صدها کیلوبایت باشد؛ نوشتن مکرر آن هم `wp_postmeta` را متورم می‌کند و هم جدول را قفل/کند.

**راه‌حل:**
1. در افزونه‌ی همراه بخش **«آخرین درخواست نمونه‌گیری‌شده»** را ببینید: ستون «سنگین‌ترین نوشتن‌های متا» دقیقاً می‌گوید چند بار و چند کیلوبایت `_elementor_element_cache` نوشته شده. اگر بالا بود، پیشنهاد می‌کنیم یک بار گزینه‌ی **«جلوگیری از نوشتن کش المنتور»** را فعال کنید و صفحه‌ی محصول/فروشگاه را در حالت مهمان چک کنید. این گزینه مقدار را در همان درخواست از کش می‌خواند (صفحه سالم می‌مانَد) ولی در دیتابیس نمی‌نویسد.
2. علت invalidate را پیدا کنید: `elementor_atomic_cache_validity__popup-trigger-styles-related-posts` نشان می‌دهد یک **ترigger پاپ‌آپ** دارید که به «نوشته‌های مرتبط» وصل است و هر بازدید آن را معتبرسازی مجدد می‌کند. اگر آن پاپ‌آپ روی همه‌ی صفحات لازم نیست، شرط نمایشش را محدود کنید (مثلاً فقط صفحه‌ی اصلی‌/یک دسته‌بندی خاص).
3. در **المنتور → ابزارها → رژنرت فایل‌ها و کش**: یک‌بار «پاک‌سازی کش/Regenerate CSS» را انجام دهید تا ردیف‌های کهنه/تکراری `_elementor_css` و کش‌های معیوب پاک شوند.
4. در **المنتور → تنظیمات → Performance**: گزینه‌های کش را بررسی کنید. اگر «عناصر داینامیک» (مثل ویجت محصولات، پاپ‌آپ، فرم) زیاد دارید، کش اختصاصی المنتور کمتر سود می‌دهد؛ در عوض **کش صفحه** (LiteSpeed Cache) را درست تنظیم کنید که بزرگ‌ترین برد در `wp_head` است.
5. اگر امکان دارد `elementor_element_cache` را غیرفعال کنید (فیلتر/تنظیم در نسخه‌های جدید) — این کش برای سایت‌های با ترافیک بالا و محتوای ثابت سود دارد، برای سایت شما که ظاهراً محتوایش پویاست دارد ضرر می‌زند.

### یافته ۴ — حلقه‌های Woodmart روی محصولات

**در لاگ چه دیدیم:** برای هر محصول در حلقه‌ها: `SELECT * FROM wp_posts WHERE ID = N LIMIT 1` + `SELECT ... FROM wp_postmeta WHERE post_id IN (N)` + کوئری‌های ویژگی.

**علت:** ویجت‌های Woodmart (مثل «محصولات مرتبط»، «پرفروش‌ها»، اسلایدرها) در بعضی تنظیمات تعداد محصولِ نمایش‌داده‌شده را زیاد می‌کنند و برای هر محصول دوباره پست و متا را می‌خوانند (کش نشده). تعداد کوئری با «تعداد محصول در حلقه × تعداد متا در هر محصول» رشد خطی دارد.

**راه‌حل:**
- در صفحه‌ی اصلی/فروشگاه، تعداد محصولات هر ویجت/اسلایدر را به حداقل لازم کاهش دهید (مثلاً از ۱۲–۱۶ به ۶–۸).
- در **Woodmart → Performance / تنظیمات قالب** گزینه‌های مربوط به «reduce queries» و غیرفعال‌سازی ویژگی‌های بی‌استفاده (swatches، brand، …) را بررسی کنید.
- اگر «محصولات مرتبط» به ووکامرس سپرده شده باشد: `woocommerce_product_related_posts` و تعدادِ مرتبط‌ها را در تنطیمات ووکامرس کاهش دهید.
- بعد از آن، تجمیع آپشن‌ها (یافته ۱) و آبجکت‌کش، بزرگ‌ترین ضرب‌کننده روی همین کوئری‌ها است.

### یافته ۵ — افزونه‌های غیرلازم که در فرانت‌اند اجرا می‌شوند

**در لاگ چه دیدیم:** `duplicator` (می‌خواند `wp_duplicator_entities`/`wp_duplicator_backups`)، `siteskill-invoice`، `siteskill-woomanager`، `RTL-CareUnit` (بررسی لایسنس/به‌روزرسانی: `rsmPluginAutoUpdateStatus`، `rtl_rsm_*`)، `code-snippets`، `classic-editor`، `health-check-allowed-plugins`، `OAuth گوگل رنک‌مث`.

هیچ‌کدام از این‌ها کاری در فرانت‌اند کاربر ندارند، ولی چون وردپرس همه‌ی افزونه‌ها را در هر درخواست اجرا می‌کند، هم فضای حافظه/اجرا می‌گیرند و هم کوئری می‌زنند.

**راه‌حل:**
- **Perfmatters** را که دارید استفاده کنید: بخش **«Script Manager»** → در حالت «Post Type = Everywhere»، افزونه‌هایی مثل Duplicator، Classic Editor، Health Check، Code Snippets را برای فرانت‌اند **disable** کنید. (این کار فایل‌هایشان را هم لود نمی‌کند.)
- افزونه‌های «مدیریتی» (تهیه‌ی نسخه‌ی پشتیبان، صدور فاکتور، بررسی لایسنس) را بهتر است فقط در زمان لازم فعال کنید، نه همیشه. حداقل Duplicator را بعد از هر بکاپ غیرفعال کنید.
- RTL-CareUnit اگر فقط کارش بررسی به‌روزرسانی/لایسنس است، گزینه‌ی «disable update check» اش را فعال کنید یا کنارش بگذارید فقط در `admin` اجرا شود.
- `health-check-allowed-plugins` نشان می‌دهد Health Check در فرانت هم دارد فایل‌ها را می‌خواند؛ در Perfmatters غیرفعالش کنید.

---

### یافته ۶ — هشدار textdomain قالب Woodmart

```
_load_textdomain_just_in_time was called incorrectly ... Translation loading for the woodmart domain was triggered too early
```
قالب، ترجمه را خیلی زود (قبل از `init`) بار می‌کند. این خودش معمولاً کند نیست، ولی نشانه‌ی این است که قالب با استانداردهای جدید وردپرس هم‌راستا نیست؛ بخش عمده‌ی کوئری‌های `woodmart_*` هم از همان‌جاست. اول آخرین نسخه‌ی قالب/woodmart-core را نصب کنید؛ اگر باقی ماند، با پشتیبانی Woodmart مطرح کنید.

---

### یافته ۷ — ووکامرس و کوئری‌های نگه‌داشت‌داده

**در لاگ چه دیدیم:** گزینه‌های HPOS/Sync، `UPDATE ... _transient_wc_term_counts` با آرایه‌ی ۴۸ عضوی (شمارش محصولات هر ترم)، کوئری‌های `wp_usermeta` و session.

**راه‌حل:**
- اگر **HPOS** (جدول سفارشات ووکامرس) را فعال کرده‌اید و «Sync» هم روشن است، اگر مطمئنید افزونه‌هایتان سازگارند، **Sync را خاموش کنید** (`woocommerce_custom_orders_table_data_sync_enabled` → no). هر Sync، کار اضافه در پس‌زمینه است.
- در **ووکامرس → وضعیت → ابزارها**: کارهای معلقِ `Action Scheduler` را پاک‌سازی کنید؛ در سایت‌های چندساله این جدول می‌تواند ده‌ها هزار ردیف داشته باشد.
- `_transient_wc_term_counts`: نگران نباشید، ولی اگر جدول `wp_options` شما خیلی بزرگ است (چند هزار ردیف/چند مگابایت) پاک‌سازی ردیف‌های `_transient_%` و `_wc_session_%` منقضی، `wp_options` را سبک می‌کند.

---

### یافته ۸ — زیرساخت: بزرگ‌ترین ضرب‌کننده‌ای که در لاگ «دیده نمی‌شود»

با این حجم کوئری و نوشتن، اگر **آبجکت‌کش پایدار** ندارید، دارید هر بازدید همه‌ی این کوئری‌ها را از نو به MySQL می‌زنید.
**چک فوری:** در صفحه‌ی افزونه‌ی همراه، بخش «وضعیت کلی → آبجکت‌کش پایدار». اگر «ندارد» بود:
1. از هاستینگ Redis/Memcached بخواهید (هاست‌های اشتراکی خوب معمولاً دارند).
2. افزونه‌ی **Redis Object Cache** را نصب و Enable کنید.
3. `wp-config.php`:
```php
define( 'WP_REDIS_HOST', '127.0.0.1' );
define( 'WP_REDIS_PORT', 6379 );
define( 'WP_CACHE_KEY_SALT', 'yenolife.com:' );
```
4. دوباره در Query Monitor ببینید: تعداد کوئری‌های `wp_options` و `wp_postmeta` باید محسوس کم شود، و TTFB پایدارتر شود.

همچنین:
- **LiteSpeed Cache**: مطمئن شوید کش صفحه واقعاً فعال و هدرها با موفقیت ست می‌شوند. برای `cart`, `checkout`, `my-account` به‌درستی exclude است. (صفحه‌ی اصلی و محصولات معمولاً +۵۰٪ سرعت می‌گیرند.)
- **ایندکس `wp_postmeta`**: بررسی کنید ایندکس `(post_id, meta_key)` یا `(meta_key, meta_value)` وجود دارد (افزونه‌ی همراه این را چک می‌کند).
- **جداول بزرگ**: `wp_posts` (revisions/autosaveها)، `wp_actionscheduler_actions/logs`، `wp_duplicator_backups` را پاک‌سازی کنید. کوئری‌های `post_name LIKE 'N-autosave%'` در لاگ نشان می‌دهد پاک‌سازی revisions می‌تواند چند ده کوئری را حذف کند.
- **PHP 8.1+** و **MySQL 8/MariaDB 10.6+** اگر هاست اجازه می‌دهد.

## ۳) نقشه‌ی اجرا (به‌ترتیب اولویت زمانی)

### «همین حالا» (۱۵ دقیقه)
1. `hanzobot-speed-doctor.zip` را نصب و فعال کنید (پیشنهاد: اول روی نسخه‌ی آزمایشی/استیجینگ).
2. صفحه‌ی **ابزارها → دکتر سرعت → «افزودن فهرست پیش‌فرض»** را بزنید، بعد دکمه‌ها: «تعمیر فوری rewrite_rules».
3. کش LiteSpeed + کش مرورگر را پاک کنید و سایت را در حالت ناشناس یک بار بگردید.
4. در Query Monitor صفحه‌ی محصول را باز کنید و شمارش کوئری `wp_options` و «Total Query Time» را یادداشت کنید.

### «امروز» (۱ ساعت)
5. آبجکت‌کش Redis را فعال کنید (اگر هاست دارد) و کار ۴ را تکرار کنید.
6. در Perfmatters → Script Manager: Duplicator، Classic Editor، Health Check، Code Snippets را در فرانت‌اند non-execute کنید.
7. در بخش «سنگین‌ترین نوشتن‌های متا» ببینید `_elementor_element_cache` چقدر است؛ اگر بالا بود گزینه‌ی جلوگیری از نوشتن‌اش را فعال و صفحات کلیدی را تست کنید.
8. المنتور: پاک‌سازی کش/Regenerate؛ محدودکردن پاپ‌آپ به صفحات لازم.
9. ووکامرس: پاک‌سازی Action Scheduler، بررسی Sync.

### «این هفته» (تصمیم‌های ریشه‌ای)
10. `hamyar-tools` و `woodmart_*_show_on_product` را در مبدأ حل کنید (توسعه‌دهنده/تنظیمات ویژگی‌ها).
11. تعداد محصولات ویجت‌های Woodmart را کم کنید و ویژگی‌های محصول بی‌استفاده را حذف/پنهان کنید.
12. مقصرِ `rewrite_rules` را از بخش رویدادهای افزونه پیدا و کد/اسنیپتش را اصلاح کنید.
13. اگر افزونه‌ای هست که دیگر واقعاً لازمتان نیست (Duplicator همیشه فعال، siteskill-*، otino، …): غیرفعال و حذف کنید. هر افزونه‌ی غیرفعال، ۳ هزینه دارد: فایل، حافظه، کوئری.

## ۴) چه چیزی را بسنجیم؟ (معیار قبلی/بعدی)

از Query Monitor این چهار عدد را قبل و بعد ثبت کنید (صفحه‌ی محصول + صفحه‌ی اصلی، حالت مهمان):

| معیار | کجا در QM | هدف |
|---|---|---|
| تعداد کل کوئری | بالای صفحه: Queries | کاهش محسوس (طوفان آپشن‌ها حل شود) |
| زمان کل کوئری | Total Query Time | زیر ~۰.۳s برای صفحات معمولی |
| تعداد کوئری روی `wp_options` | بخش Queries → فیلتر Caller | باید به ۱–۳ کوئری برسد |
| TTFB (کروم → Lighthouse یا `curl -w %{time_starttransfer}`) | — | کاهش پیوسته |

## ۵) دام‌ها — این کارها را نکنید

- **همه‌ی ترنزینت‌ها را پاک نکنید.** حذف `_transient_*`های فعال باعث می‌شود ووکامرس/المنتور همه‌چیز را دوباره بسازد و سایت موقتاً کندتر شود.
- **افزونه‌های «بهینه‌ساز» تکراری نصب نکنید.** شما الان هم LiteSpeed Cache دارید و هم Perfmatters؛ افزودن Autoptimize/WP Rocket دوباره = تداخل و کندی.
- **المنتور را کورکورانه غیرفعال نکنید** (با قالب Woodmart و صفحه‌ساز وابسته). اول کش را کنترل کنید.
- **`flush_rewrite_rules()` را در هر بار بازدید یا در `init` صدا نزنید.** این همان چیزی است که الان دارد سایت را کند می‌کند.
- کش صفحه را برای `cart/checkout/my-account` فعال نکنید (افزونه‌ی ما هم روی همین مسیرها کار می‌کند).

## پیوست: افزونه‌ی «دکتر سرعت هَنزبات»

مسیر: `hanzobot-speed-doctor/` (برای نصب: زیپ `hanzobot-speed-doctor.zip` را از پیشخوان نصب کنید، یا پوشه را در `wp-content/plugins` بگذارید).

| بخش | کار |
|---|---|
| تجمیع کوئری‌های آپشن | یادگیری نام آپشن‌های تک‌کوئری + پرکردن همه با یک `IN (...)` + علامت‌زدن ناموجودها در `notoptions` |
| نگهبان rewrite_rules | حذف نوشتن‌های تکراری + تعمیر ردیف با `INSERT ... ON DUPLICATE KEY UPDATE` + `autoload=off` + ثبت مقصر |
| پروفایلر | شمارش حجم/تعداد نوشتن‌ها در `wp_postmeta` و `wp_options` (مثلاً کش المنتور) |
| گزارش | autoload، ترنزینت‌ها، ایندکس postmeta، وضعیت آبجکت‌کش، ردیف‌های کش المنتور |
| گزینه‌ی پیشرفته | جلوگیری از نوشتن `_elementor_element_cache` (پیش‌فرض خاموش) |

**نکات مهم:**
- هیچ داده‌ای به بیرون فرستاده نمی‌شود؛ همه‌چیز در خود سایت است.
- این افزونه **داروی موقت + ابزار تشخیص** است. بعد از اینکه موارد ۱ تا ۳ حل شد، می‌توانید غیرفعالش کنید (یا فقط «نگهبان» را روشن بگذارید).
- اگر API سایت شما (رست‌اپی hamyar) را مصرف می‌کند، این افزونه دخالتی در پاسخ‌ها نمی‌کند.
